# 165 FPS 丢帧分类与单帧预算

## 测量方法

`tests/measure_165_frame_drops.ps1` 通过软件自己的控制接口，在真实 2560×1440
副屏滚动同一项目文档，依次测原画质预算、400 Mbps 预算、原预算。
每轮预热后取约 90 秒的累计计数差，保留 165 FPS、4:4:4、明文 UDP、FEC、
允许撕裂、900 Mbps 线路预算及同一控制连接。结束恢复原画质预算。

画质预算通过 `预算 Mbps × 1000000 / 8 / 165` 换算编码单帧上限，编码器
还会按测得的发送能力自适应收紧它。因此配置值、实际帧大小和实际总码率
不是同一个数。较低预算测试只用于对照，未验证其视觉质量。

## 计数含义

| 遥测字段 | 含义 |
| --- | --- |
| `network_started_frames` | 接收器开始组装的帧数；整帧所有包均未出现时不会计入 |
| `network_incomplete_frames` | 未收齐就被下一帧替代的整帧数 |
| `incomplete_packets` | 这些不完整帧里未收齐的编码数据块数，不能作为丢帧数 |
| `freshness_dropped_frames` | 已收齐、但尚未被消费者取走就被新帧覆盖的帧数 |
| `decoder_invalid_frames` | 解码器拒收了该帧的编码数据块 |
| `decoder_not_ready_frames` | 推送数据块后解码器仍不具备完整帧条件 |
| `decoder_failed_frames` | 完整帧条件成立，但解码/绘制调用失败 |
| `presented_frames` | 已进入 Present 提交的帧数，不代表面板完整扫描次数 |
| `network_queue_dropped_frames` | 发送端待发帧被更新帧覆盖，不是笔记本丢帧 |
| `etw_dropped_presents` | Windows 显示事件标记的 dropped Present，事件统计可能延后到达 |

接收端丢帧事件按“未收齐、待处理覆盖、解码拒收”分别统计。
不能把目标 165 与实际 FPS 的差额都归为网络丢包。未收齐也可能包含乱序、
过滤驱动或系统调度影响，不是网线上物理丢包率的证明。

发送端和接收端各自使用本机累计计数与持续时间，不直接相减两端帧数，
以免异步遥测窗口错位。相邻阶段在采样边界可有 1–2 帧正在处理，分析脚本
报告这些差额并检查计数一致性。逐秒 P95 的中位数不是所有帧汇总的 P95。

## 本机证据

- `results/165-frame-drops.jsonl`：逐秒原始遥测。
- `results/165-frame-drops-summary.json`：分类计数、实际单帧大小与发送耗时。
- `results/165-frame-drops-validation.json`：测试条件与原预算恢复。
- `results/165-frame-drops-final-verification.json`：两端部署、正常构建、显示与网络设置。

统计仅增加逐帧常数次计数和每秒输出，不启用逐帧 GPU fence 观察器或
包捕获，也不更改网卡配置。软件仍只保留最新待处理帧，不增加播放缓冲。
